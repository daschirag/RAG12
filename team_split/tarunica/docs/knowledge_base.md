## Real fault taxonomy (from event_info.csv, farms A-C)

95 events: 45 anomaly (A 12, B 6, C 27) and 50 normal. The dataset README says 44 anomaly datasets; the
event_info files contain 45, and the files are what this project uses. Farm A descriptions are short component
labels ("Hydraulic group", "Gearbox failure"); Farm B describes transformer over-temperature and rotor/main bearing
damage; Farm C has detailed, sometimes multi-fault, partly German-language logbook text with error codes.

Each description is mapped by keyword rules (`taxonomy.COMPONENTS`) to wind-turbine components; `+`-joined
descriptions map to several components and the primary one is the first mentioned. All 45 events map to a
component. Primary-component counts: pitch system 8, hydraulic system 6, gearbox 5, transformer 5, communication
and control 4, auxiliary electrical and safety chain 4, rotor/main bearing 3, blades/hub/structure 3, generator
bearings 2, power converter 2, cooling 1, rotor brake 1, yaw 1 (table per farm in `results/kb/kb_summary.md`).
`default_severity` per component (high for drive train, transformer and converter; medium for auxiliaries;
low for communication and minor structural items) is a project assumption for B5, not a dataset label.

### How this differs from the plan's fault list
The plan lists solar-inverter faults (inverter overheating, abnormal voltage, abnormal current, underperformance,
sensor anomaly, power-generation deviation). The labelled fault data is wind-turbine SCADA, and its events are
**component failures**, not electrical symptom classes:
- No inverter events exist. The nearest analogues of "inverter overheating" are transformer over-temperature
  (5 events) and two power-converter events (the wind turbine's power electronics).
- "Abnormal voltage" and "abnormal current" each have one loose analogue (Farm C: pitch-axis DC-link voltage low;
  auxiliary current measurement fault).
- Underperformance, sensor anomaly and power-generation deviation are not event labels. They could be derived
  from SCADA (status_type 1 = derated; power vs power curve) but are not in event_info.csv.
So fault diagnosis (B4) will classify wind-turbine components. The plan's solar-inverter fault types appear in
the knowledge base only as clearly labelled synthetic manual and troubleshooting sections.

## Document types and provenance

| doc_type | count | source | synthetic |
|---|---|---|---|
| fault_description | 45 | one per real anomaly event: farm, asset, window, original description, derived components | no |
| scada_knowledge | 54 | per-farm event overviews incl. normal-behaviour windows (3); per-farm, per-component event histories, counting secondary components too (17); per-farm sensor catalogues by component (from feature_description.csv) and "other" sensors (34) | no |
| equipment_manual | 19 | 13 wind components + 6 plan solar-inverter fault types | yes |
| troubleshooting_procedure | 19 | same coverage as manuals: ordered checks and corrective actions | yes |
| maintenance_record | 45 | one invented work order per real anomaly event (visit the day after the window) | yes |
| standard_summary | 7 | short original scope overviews: IEC 61400-1, 61400-12-1, 61400-25, IEC 61724-1, IEC 62446-1, ISO 17359, ISO 55000 | yes |

Schema (`schema.KBDocument`, pydantic): `doc_id`, `doc_type`, `title`, `text`, `domain` (wind / solar / general),
`synthetic`, `component` + `components`, `farm`, `asset_id`, `event_id`, `severity`, `tags`, `provenance`,
`content_sha256`.
- Real documents: `provenance.source = "dataset"`, `source_file` (repo-relative) and `source_rows` (0-based data
  rows, header excluded). Tests check the rows exist and that a fault document's row is that event.
- Synthetic documents: `synthetic = true`, `provenance.source = "generated"`, `generator = src/backend/kb/content.py`,
  and the marker `[SYNTHETIC]` in both title and text (enforced by the schema). Synthetic maintenance records
  reference a real event id and window but say explicitly that their findings and actions are invented.
- `content_sha256` of the text, checked by `validate_kb`, so later phases (C3 document trust) can detect edits.

Synthetic text: written for this project as general engineering guidance in our own words. No manufacturer
manual or standard text is copied or paraphrased clause by clause; standard overviews state only the general
scope of each standard and say to consult the official document. Real sensor names are inserted into the
synthetic manuals from feature_description.csv (and said to be real).

## Storage and ingestion (reuses the existing pipeline)
- `documents.jsonl`: one KBDocument per line (full metadata, provenance, hash).
- `chunks.jsonl`: the existing ingestion format `{chunk_id, domain_id, text, metadata}`, written with
  `ingestion.pipeline._write_jsonl`; chunk ids `<doc_id>::<i>`, metadata flattened to scalars so the local and
  Azure vector stores accept it unchanged. B1 chunker: paragraph packing up to 1200 body characters, title
  prefixed to every chunk (189 documents -> 210 chunks). B2 compares chunking strategies.
- New domain manifest `config/domain_manifests/knowledge_base.yaml`, so `POST /ingest/knowledge_base`,
  `/query/knowledge_base` and `/ask/knowledge_base` work through the existing endpoints (tested with the fake
  store). The console UI shows the new domain with its default style until I2.

## Data quirks found
- `feature_description.csv` of farms A and B stores the degree sign as the Unicode replacement character
  U+FFFD; Farm C uses "Celsius"/"deg". Units are normalised to ASCII (`degC`, `deg`).
- The asset column is `asset` in Farm A and `asset_id` in B/C (normalised to `asset_id`).
- 45 anomaly events in the files vs 44 in the README.
- The README states the data source (Farm A: EDP open data; B, C anonymised offshore farms) but no license; the
  KB cites file paths and rows and makes no license claim.

## B2 Chunking comparison

Code: `src/backend/kb/chunking.py` (three strategies), `queries.py` (labelled set), `retrieval_eval.py`
(metrics, exact cosine index). Run: `python -m experiments.chunking_comparison` ->
`results/kb/b2_chunking_summary.md`, `b2_chunking_metrics.csv` (per query and method), `b2_chunk_stats.csv`,
`b2_paired_bootstrap.csv`. Tests: `tests/test_kb_chunking.py` (mock embeddings).

Setup: the 189 B1 documents; all-MiniLM-L6-v2 (the local vector store's model) for indexing and for the semantic
chunker's boundaries; exact cosine search; top 5 chunks; 64 labelled queries with document-level graded relevance
(2 = the document asked about, 1 = closely related). Precision/recall/nDCG count each document once, so repeated
chunks of one document are not rewarded. 95% CIs by resampling queries; paired bootstrap between methods.

| method | chunks | mean chars | Precision@5 | Recall@5 | MRR | nDCG@5 |
|---|---|---|---|---|---|---|
| (A) fixed_size (800/100) | 248 | 570 | 0.197 [0.166, 0.228] | 0.602 [0.508, 0.695] | 0.606 [0.507, 0.704] | 0.574 [0.483, 0.662] |
| (B) semantic | 370 | 366 | **0.231** [0.203, 0.259] | **0.695** [0.609, 0.773] | **0.707** [0.618, 0.795] | **0.667** [0.585, 0.746] |
| (C) metadata_aware | 222 | 762 | 0.194 [0.163, 0.225] | 0.594 [0.500, 0.688] | 0.632 [0.529, 0.731] | 0.581 [0.490, 0.669] |

- **Semantic chunking is best on every metric.** Paired bootstrap, nDCG@5: semantic - fixed +0.094
  [+0.043, +0.146]; semantic - metadata-aware +0.086 [+0.029, +0.143]. For MRR, semantic - metadata-aware
  +0.075 [-0.001, +0.151] (borderline).
- **Metadata-aware is not better than fixed-size** (nDCG difference 0.007, CI [-0.024, +0.041]). This contradicts
  the expectation that the metadata header would help. It helps where the query names metadata that the body
  text lacks (maintenance 0.333 vs 0.176; count 0.667 vs 0.557; solar 0.867 vs 0.832), but not for event
  queries (0.109 vs 0.122 fixed, 0.377 semantic).
- **Confound: chunk size.** The strategies produce different chunk sizes (366 / 570 / 762 characters), so this
  comparison measures boundary rule and size together. Smaller semantic chunks isolate the short "Wind Farm C,
  turbine asset 21" line of a fault description, which matches event queries; long metadata-aware chunks dilute
  it. A size-matched comparison was not run, because choosing it after seeing these numbers would tune on the
  evaluation set. It needs a separate query split.
- **Precision@5 is low for all methods (about 0.2)** because most queries have only 1-2 relevant documents: the
  maximum possible precision with 2 relevant documents is 0.4.
- **Query-set caveats**: queries are template-generated and relevance is by construction, so they measure how
  well each strategy retrieves the source documents of known facts, not real user questions. Troubleshooting
  queries quote a symptom that appears verbatim in the manual (graded 1), not in the troubleshooting procedure
  (graded 2). Standards queries are easy (nDCG 1.0 for all methods).

## B3 Retrieval comparison

Code: `src/backend/retrieval/query_classifier.py` (conceptual vs quantitative), `src/backend/retrieval/hybrid_retriever.py`
(BM25, reciprocal rank fusion, cross-encoder reranking, classifier routing). Run:
`python -m experiments.retrieval_comparison` -> `results/kb/b3_retrieval_summary.md`, `b3_retrieval_metrics.csv`,
`b3_paired_bootstrap.csv`, `b3_classifier.csv`, `b3_run.json`. Tests: `tests/test_hybrid_retrieval.py`.

Setup: B2's semantic chunks (370) of the B1 knowledge base; the 64 labelled queries; document-level metrics, top 5.
The chunking was chosen as B2's best on the same query set, which slightly favours it. BM25 (k1 1.5, b 0.75) is
implemented in the repo; vector = all-MiniLM-L6-v2 exact cosine; hybrid = reciprocal rank fusion (k = 60) of the
BM25 and vector top 50; rerank = `cross-encoder/ms-marco-MiniLM-L-6-v2` (88 MB, in D:\Rag\cache) over the hybrid
top 20; routed = quantitative -> BM25, conceptual -> hybrid + rerank (rule fixed before the run).

| variant | Precision@5 | Recall@5 | MRR | nDCG@5 | ms/query (CPU) |
|---|---|---|---|---|---|
| bm25 | 0.241 | 0.695 | 0.743 | 0.650 [0.567, 0.730] | 0.5 |
| vector | 0.231 | 0.695 | 0.707 | 0.667 [0.585, 0.746] | 33.1 |
| hybrid_rrf | 0.266 | 0.781 | 0.826 | 0.752 [0.689, 0.810] | 35.7 |
| **hybrid_rerank** | **0.269** | **0.789** | **0.958** | **0.835** [0.787, 0.878] | 1047.4 |
| routed | 0.259 | 0.766 | 0.880 | 0.781 [0.713, 0.845] | 941.2 |

- BM25 and vector are statistically tied (nDCG -0.017, CI [-0.105, +0.069]) but complementary: BM25 is better on
  event (0.622 vs 0.377) and maintenance queries, which name farms, assets and event ids; vector is better on
  signals and count queries.
- Fusion helps: hybrid beats BM25 (+0.102, CI [+0.041, +0.162]) and vector (+0.085, CI [+0.029, +0.142]).
- Reranking helps further: hybrid + rerank beats hybrid (+0.083, CI [+0.044, +0.123]); MRR rises from 0.826 to
  0.958. Cost: about 1 s per query on CPU (30x hybrid), from scoring 20 (query, passage) pairs.
- **Routing hurt.** The fixed rule sent the 6 quantitative (count) queries to BM25, which scores 0.190 on them vs
  0.760 for hybrid + rerank: "How many hydraulic system failures in Wind Farm A?" matches many individual fault
  documents lexically rather than the event-history summary that holds the count. Routed is worse than plain
  hybrid + rerank (-0.053, CI [-0.101, -0.018]). For this knowledge base, quantitative questions are not
  well served by keyword search; B5 uses hybrid + rerank for all queries, and the classifier's role is to decide
  whether a question needs numbers computed from data (the deterministic numeric path) rather than to pick the
  retriever. The routing rule was not changed after seeing these results.
- Query classifier: 64/64 on the labelled set and 10/10 on the hand-written examples in
  `tests/test_hybrid_retrieval.py`. **Neither is an independent estimate**: the rules were written with the query
  templates in view, and the 10 examples were written by the same author in the same session as the rules. The
  classifier's accuracy has not been independently measured; citing it needs a query set written by someone else
  (or before the rules were fixed), scored without changing the rules.

### Production retrieval configuration (used by B5 and B6)
**GreenRAG retrieves with hybrid search (BM25 + MiniLM vector, reciprocal rank fusion, top 50 each) followed by
cross-encoder reranking of the top 20 (`cross-encoder/ms-marco-MiniLM-L-6-v2`), over the semantic chunks of the
knowledge base.** The query classifier does **not** route retrieval (routing was tested and hurt). Its only role
is to flag that a question needs a numeric/computed answer, which is then produced deterministically from the data
(as the existing numeric path of /ask does) instead of being generated by the LLM from retrieved text.
- Only 6 count queries: per-class numbers for "quantitative" are indicative only.
