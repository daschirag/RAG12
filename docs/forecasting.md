# Track A - Forecasting: design notes

## A1 Preprocessing (`src/backend/forecasting/preprocess.py`)

Run: `python -m experiments.preprocess_solar`. Outputs in `results/forecasting/`
(`preprocessing_report_plant{1,2}.json`, `preprocessing_summary.md`, `preprocessing_plant{1,2}.png`);
cleaned frames in `data/processed/forecasting/` (gitignored, regenerated by the command).

### What the raw data looks like (measured, see the JSON reports)
| | Plant 1 | Plant 2 |
|---|---|---|
| 15-min slots (34 days) | 3264 | 3264 |
| slots with no generation rows | 106 (mostly night, longest gap 9 h) | 5 |
| slots with no weather row | 82 | 5 |
| slots with only some of 22 inverters | 101 | 904 (459 in daytime) |
| median DC/AC ratio | 10.22 (DC scale inconsistency) | 1.02 |
| duplicates / off-grid timestamps | 0 / 0 | 0 / 0 |

Plant 1 is clean (daytime AC vs irradiation correlation 0.988 after cleaning) and is the primary
modelling series. Plant 2 has long periods with 4 inverters absent and intermittent mid-day zeros on
several inverters (correlation 0.732); it is kept as a harder secondary series.

### Pipeline and decisions
Every step is causal: the output at time t depends only on rows at or before t. This is tested by
running the pipeline on data truncated at T and requiring an identical result up to T
(`test_pipeline_is_causal_prefix_invariant`). The test fails if a centered window or whole-series
statistic is introduced (checked by mutation during A1).

1. **Duplicates**: exact duplicate rows dropped; rows sharing a (timestamp, inverter) key with
   different values are all dropped, since the correct one cannot be known. Both counted.
2. **Time sync**: timestamps parsed with explicit formats (Plant 1 generation is `dd-mm-yyyy HH:MM`),
   snapped to the 15-min grid within +/-2 min (others dropped), reindexed onto one regular grid
   shared by generation and weather.
3. **Plant aggregation**: plant AC = mean AC over reporting inverters x 22. Scaling the mean keeps the
   total comparable when inverter rows are missing. *Assumption*: absent inverters behaved like the
   reporting ones. If they were actually offline (possible for Plant 2, 21-29 May) the total is
   overstated. `inverter_coverage` is kept so this can be analysed; below 50% coverage the target is NaN.
   DC power is not carried forward because of the Plant 1 scale problem and because it is concurrent
   with the target.
4. **Physical bounds**: AC in [0, 22 x 1500 kW] (nameplate is not in the dataset; 1500 kW is above the
   largest observed per-inverter value 1410.95 kW), irradiation in [0, 1.5], ambient in [-10, 60] C,
   module in [-10, 90] C. Violations become NaN and are flagged. AC > 1 kW while irradiation is 0 is
   physically inconsistent and becomes NaN.
5. **Missing values**: weather forward-filled for at most 2 slots (30 min), flagged. A missing target
   at a slot with no generation rows and *observed* zero irradiation is set to 0 (no sun, no output).
   All other gaps stay NaN; they are not interpolated, because interpolation uses the next observation.
   Downstream phases drop NaN targets, and evaluation will use observed targets only.
6. **Statistical outliers**: robust z-score of AC/irradiation (daytime, irradiation > 0.1) against a
   trailing 7-day window that excludes the current value; |z| > 5 is flagged. Values are **kept**,
   because they may be real events (inverter trips, soiling); A5 error analysis can use the flags.
7. **Noise**: causal 3-slot rolling median copies of the weather inputs (`*_smooth`); raw columns kept.
   The target is never smoothed. The effect is reported as mean absolute first difference, raw vs smooth.
8. **Normalization**: `TrainOnlyScaler` (standard or min-max) fits on the training frame only, after
   `chronological_split`, which splits on whole calendar days in time order (no shuffling).

### Not available
- **Humidity**: the plan lists humidity, but the dataset has no humidity column. None is invented. An
  external source (e.g. reanalysis data for the plant location) would need the plant coordinates,
  which the dataset does not give, and requires user approval.

## A2 Feature engineering (`src/backend/forecasting/features.py`)

Run: `python -m experiments.features_solar` -> `results/forecasting/features_summary.md`, `features_plant{1,2}.json`.

### Resolution and horizon (fixed for all A3 models)
- **Resampling interval: none, keep the native 15-min grid.** The record is only 34 days (3264 slots).
  Hourly resampling would leave 816 rows (about 440 in daylight), too few for the LSTM and the advanced
  model, and averaging would hide the cloud-driven ramps that make short-term solar forecasting hard.
- **Horizon: 1 hour ahead (H = 4 steps).** Each row is a forecast origin t (last observed slot); the target
  is plant AC power at T = t + 1 h. This is an intraday operational horizon (dispatch, reserve). The dataset
  has no numerical weather forecasts, so at longer horizons predictions collapse to the daily profile.
- The plan's lags 1/3/6/24 are 15-min steps before the origin (15 min, 45 min, 1.5 h, 6 h). Because solar
  output is dominated by the daily cycle, `ac_same_slot_yesterday` = y(T - 24 h) is added.

### Information available at the origin
All features use data at times <= t. The only exceptions are still known at t: calendar features of T
(deterministic) and `irr_envelope_target`, the maximum irradiation at T's time-of-day slot over days strictly
before T's date (all <= T - 24 h < t). Rolling windows end at t, which is H steps before the target.

Measured weather at T is future information. It is excluded by default. `FeatureConfig(include_oracle_weather=True)`
adds `oracle_irr_target`, which is only for a clearly labelled "perfect weather forecast" upper bound.

### Leakage tests (`tests/test_forecasting_features.py`)
- Target alignment: y(row t) == AC(t + 1 h) exactly; lag and rolling values checked against raw values.
- Future corruption: every value after a random daytime origin t (3 seeds) is replaced with noise; the
  features of row t and of every earlier row must be unchanged. The same corruption *does* change
  `oracle_irr_target`, which shows the test can detect future information.
- Envelope uses previous days only; split segments are disjoint and ordered.

### Split (by the day of the target time)
train 21 days (targets 05-15 to 06-04), val 4 (06-05 to 06-08), calib 4 (06-09 to 06-12, reserved for A4
conformal calibration), test 5 (06-13 to 06-17). Assigning rows by target day means no training target lies
in a later segment. Plant 1: 1901 / 379 / 384 / 478 rows (daytime 905 / 188 / 188 / 234).

### Constraints carried into A3
- Some features are missing in part of the training data, e.g. 16-slot rolling stats (269 of 1901 Plant 1 train
  rows), because a single missing slot blanks the window. All models must be scored on the **same** test rows:
  models that cannot take NaN get a train-fitted imputer and do not drop rows.
- `month` has two values (5, 6) and `day` behaves like a trend over 34 days. Both can extrapolate poorly;
  they are kept as the plan requires, and their effect will show in A3/A5 results.
- The test set is 5 days (234 daytime rows for Plant 1), so differences between models will carry wide
  uncertainty; A5 will report this.
