# Track A - Forecasting: design notes

## A1 Preprocessing (`src/backend/forecasting/preprocess.py`)

Run: `python -m experiments.preprocess_solar`. Outputs in `results/forecasting/`
(`preprocessing_report_plant{1,2}.json`, `preprocessing_summary.md`, `preprocessing_plant{1,2}.png`);
cleaned frames in `data/processed/forecasting/` (gitignored, regenerated by the command).

### What the raw data looks like (measured, see the JSON reports)
| | Plant 1 | Plant 2 |
|---|---|---|
| 15-min slots (34 days) | 3264 | 3264 |
| slots with no generation rows | 106 (mostly night, longest gap 9 h) | 5 |
| slots with no weather row | 82 | 5 |
| slots with only some of 22 inverters | 101 | 904 (459 in daytime) |
| median DC/AC ratio | 10.22 (DC scale inconsistency) | 1.02 |
| duplicates / off-grid timestamps | 0 / 0 | 0 / 0 |

Plant 1 is clean (daytime AC vs irradiation correlation 0.988 after cleaning) and is the primary
modelling series. Plant 2 has long periods with 4 inverters absent and intermittent mid-day zeros on
several inverters (correlation 0.732); it is kept as a harder secondary series.

### Pipeline and decisions
Every step is causal: the output at time t depends only on rows at or before t. This is tested by
running the pipeline on data truncated at T and requiring an identical result up to T
(`test_pipeline_is_causal_prefix_invariant`). The test fails if a centered window or whole-series
statistic is introduced (checked by mutation during A1).

1. **Duplicates**: exact duplicate rows dropped; rows sharing a (timestamp, inverter) key with
   different values are all dropped, since the correct one cannot be known. Both counted.
2. **Time sync**: timestamps parsed with explicit formats (Plant 1 generation is `dd-mm-yyyy HH:MM`),
   snapped to the 15-min grid within +/-2 min (others dropped), reindexed onto one regular grid
   shared by generation and weather.
3. **Plant aggregation**: plant AC = mean AC over reporting inverters x 22. Scaling the mean keeps the
   total comparable when inverter rows are missing. *Assumption*: absent inverters behaved like the
   reporting ones. If they were actually offline (possible for Plant 2, 21-29 May) the total is
   overstated. `inverter_coverage` is kept so this can be analysed; below 50% coverage the target is NaN.
   DC power is not carried forward because of the Plant 1 scale problem and because it is concurrent
   with the target.
4. **Physical bounds**: AC in [0, 22 x 1500 kW] (nameplate is not in the dataset; 1500 kW is above the
   largest observed per-inverter value 1410.95 kW), irradiation in [0, 1.5], ambient in [-10, 60] C,
   module in [-10, 90] C. Violations become NaN and are flagged. AC > 1 kW while irradiation is 0 is
   physically inconsistent and becomes NaN.
5. **Missing values**: weather forward-filled for at most 2 slots (30 min), flagged. A missing target
   at a slot with no generation rows and *observed* zero irradiation is set to 0 (no sun, no output).
   All other gaps stay NaN; they are not interpolated, because interpolation uses the next observation.
   Downstream phases drop NaN targets, and evaluation will use observed targets only.
6. **Statistical outliers**: robust z-score of AC/irradiation (daytime, irradiation > 0.1) against a
   trailing 7-day window that excludes the current value; |z| > 5 is flagged. Values are **kept**,
   because they may be real events (inverter trips, soiling); A5 error analysis can use the flags.
7. **Noise**: causal 3-slot rolling median copies of the weather inputs (`*_smooth`); raw columns kept.
   The target is never smoothed. The effect is reported as mean absolute first difference, raw vs smooth.
8. **Normalization**: `TrainOnlyScaler` (standard or min-max) fits on the training frame only, after
   `chronological_split`, which splits on whole calendar days in time order (no shuffling).

### Not available
- **Humidity**: the plan lists humidity, but the dataset has no humidity column. None is invented. An
  external source (e.g. reanalysis data for the plant location) would need the plant coordinates,
  which the dataset does not give, and requires user approval.

## A2 Feature engineering (`src/backend/forecasting/features.py`)

Run: `python -m experiments.features_solar` -> `results/forecasting/features_summary.md`, `features_plant{1,2}.json`.

### Resolution and horizon (fixed for all A3 models)
- **Resampling interval: none, keep the native 15-min grid.** The record is only 34 days (3264 slots).
  Hourly resampling would leave 816 rows (about 440 in daylight), too few for the LSTM and the advanced
  model, and averaging would hide the cloud-driven ramps that make short-term solar forecasting hard.
- **Horizon: 1 hour ahead (H = 4 steps).** Each row is a forecast origin t (last observed slot); the target
  is plant AC power at T = t + 1 h. This is an intraday operational horizon (dispatch, reserve). The dataset
  has no numerical weather forecasts, so at longer horizons predictions collapse to the daily profile.
- The plan's lags 1/3/6/24 are 15-min steps before the origin (15 min, 45 min, 1.5 h, 6 h). Because solar
  output is dominated by the daily cycle, `ac_same_slot_yesterday` = y(T - 24 h) is added.

### Information available at the origin
All features use data at times <= t. The only exceptions are still known at t: calendar features of T
(deterministic) and `irr_envelope_target`, the maximum irradiation at T's time-of-day slot over days strictly
before T's date (all <= T - 24 h < t). Rolling windows end at t, which is H steps before the target.

Measured weather at T is future information. It is excluded by default. `FeatureConfig(include_oracle_weather=True)`
adds `oracle_irr_target`, which is only for a clearly labelled "perfect weather forecast" upper bound.

### Leakage tests (`tests/test_forecasting_features.py`)
- Target alignment: y(row t) == AC(t + 1 h) exactly; lag and rolling values checked against raw values.
- Future corruption: every value after a random daytime origin t (3 seeds) is replaced with noise; the
  features of row t and of every earlier row must be unchanged. The same corruption *does* change
  `oracle_irr_target`, which shows the test can detect future information.
- Envelope uses previous days only; split segments are disjoint and ordered.

### Split (by the day of the target time)
train 21 days (targets 05-15 to 06-04), val 4 (06-05 to 06-08), calib 4 (06-09 to 06-12, reserved for A4
conformal calibration), test 5 (06-13 to 06-17). Assigning rows by target day means no training target lies
in a later segment. Plant 1: 1901 / 379 / 384 / 478 rows (daytime 905 / 188 / 188 / 234).

### Constraints carried into A3
- Some features are missing in part of the training data, e.g. 16-slot rolling stats (269 of 1901 Plant 1 train
  rows), because a single missing slot blanks the window. All models must be scored on the **same** test rows:
  models that cannot take NaN get a train-fitted imputer and do not drop rows.
- `month` has two values (5, 6) and `day` behaves like a trend over 34 days. Both can extrapolate poorly;
  they are kept as the plan requires, and their effect will show in A3/A5 results.
- The test set is 5 days (234 daytime rows for Plant 1), so differences between models will carry wide
  uncertainty; A5 will report this.

## A3 Models (`src/backend/forecasting/models.py`)

Run: `python -m experiments.train_forecasters` -> `results/forecasting/a3_summary.md`, `a3_metrics.csv`,
`a3_predictions_plant{1,2}.csv` (raw per-row predictions), `a3_run.json` (chosen hyperparameters, fit times,
environment).

### Common protocol (identical for every model)
- A2 features, horizon 1 h (4 steps), split train 21 / val 4 / calib 4 (unused in A3) / test 5 days.
- **Same scored rows**: val/test rows whose target was observed. The night slots A1 filled with 0 are not
  scored. No model drops rows.
- **Missing inputs**: `TrainOnlyImputer` fills NaN with the training-split median for the same hour of T
  (fallback: training global median). Sequence models fill per-slot inputs the same way from the training
  period and add missing-value indicator channels.
- **Post-processing**: predictions clipped to [0, 33,000 kW] (22 x 1500 kW), and set to 0 when T's slot is night
  according to the irradiation envelope from previous days (known at the origin).
- **Model selection on val only**; test is scored once. Seeds 0, 1, 2 for every model with randomness;
  results reported as mean +/- sample std.
- CPU only: the installed torch 2.13.0 is a CPU build (no CUDA). The data is small (about 1,900 training rows),
  so this costs little, and CPU runs are exactly repeatable with fixed seeds.

### Models
| model | description |
|---|---|
| persistence | y_hat(t + 1 h) = y(t) |
| daily_persistence | y_hat(T) = y(T - 24 h) |
| random_forest | sklearn RF, 300 trees; grid max_depth {None, 12} x min_samples_leaf {1, 5} x max_features {1.0, 0.5} |
| xgboost | hist trees, subsample/colsample 0.8, early stopping (50 rounds) on val MAE; grid max_depth {3, 5} x learning_rate {0.03, 0.1} |
| lstm | 1-layer LSTM (hidden 32) over a 24-step (6 h) window ending at t, plus a context vector for T, MLP head |
| tcn | **advanced temporal model**: temporal convolutional network, 4 residual causal blocks, dilations 1/2/4/8, kernel 3 (receptive field 31 >= 24-step window), 32 channels, same inputs and head as the LSTM |
| xgboost_no_day_month | ablation: xgboost without `day`/`month` |
| xgboost_oracle_weather | **upper bound only**: adds measured irradiation at T (future). Not deployable |

Sequence inputs per slot: AC power, irradiation, ambient and module temperature (scaled with training-period
statistics), missing indicators for AC and irradiation, time-of-day sin/cos. Context for T: time-of-day sin/cos,
irradiation envelope, AC and irradiation at T - 24 h. Adam (lr 1e-3, weight decay 1e-4), batch 64, MSE loss,
up to 300 epochs, early stopping on val MAE (patience 25), best epoch restored.

**Why a TCN as the advanced model**: with about 1,900 training windows, a model has to be small. A TCN uses
dilated causal convolutions, so its output depends only on past steps (tested), it trains in parallel rather
than step by step, and it has few parameters. Giving it exactly the LSTM's inputs and head makes the
comparison about architecture alone. Transformer-type models (e.g. TFT) need far more data than 34 days.

### Reproducibility fixes found by the tests
- Random Forest predict is run single-threaded: parallel predict summed tree outputs in thread-completion
  order and changed the last bits (up to 1.3e-11 kW) between identical runs.
- torch runs with `use_deterministic_algorithms(True)` and seeded generators; identical seeds give identical
  predictions (tested for both LSTM and TCN).

TCN best epoch 16 / 12 (24,065 parameters).

## A4 Uncertainty-aware forecasting (`src/backend/forecasting/uncertainty.py`)

Run: `python -m experiments.uncertainty_solar` -> `results/forecasting/a4_summary.md` (all tables),
`a4_metrics.csv`, `a4_coverage_by_tod.csv`, `a4_coverage_by_day.csv`, `a4_intervals_plant{1,2}.csv` (raw
bounds per row, method, level, seed), `a4_night_rule.{csv}`, `a4_run.json`, figures `a4_interval_plant1.png`,
`a4_coverage_tod.png`.

### What "confidence" means
**Confidence is the nominal coverage level of the prediction interval** (0.80, 0.90 or 0.95). A forecast with
`confidence = 0.90` comes from a method that targets containing the observed value in 90% of cases *over many
forecasts*. It is **not** the probability that the point prediction is correct (a continuous point forecast is
essentially never exactly right), and it is not a per-forecast probability. The achieved (empirical) coverage
can differ from the nominal level; A4 measures it. The same definition is the `confidence` field description
in `src/backend/forecasting/schemas.py` (`ForecastResponse`), used by POST /forecast in A6.

### Data roles (no test data in any choice)
| split | days (target time) | used for |
|---|---|---|
| train | 05-15 to 06-04 | fitting point and quantile models, imputer statistics |
| val | 06-05 to 06-08 | hyperparameters (point: MAE; quantile: mean pinball), early stopping, night-rule decision |
| calib | 06-09 to 06-12 | calibration of gaussian / split_conformal / CQR (only its y is read) |
| test | 06-13 to 06-17 | scored once |

`tests/test_forecasting_uncertainty.py` checks that the intervals do not change when the test targets are
replaced with garbage, and (positive control) that they do change when the calibration targets change.

### Methods (same base models for all)
Point model: XGBoost as in A3. Quantile model: one multi-quantile XGBoost (`reg:quantileerror`) for
quantiles 0.025/0.05/0.1/0.5/0.9/0.95/0.975, grid max_depth {3, 5} x learning_rate {0.03, 0.1} chosen on val
mean pinball loss; crossing quantiles are sorted per row (rearrangement).

| method | role | interval |
|---|---|---|
| qr_raw | baseline (a) | quantile-regression bounds, no calibration |
| gaussian | baseline (b) | point +/- z(level) * sigma; sigma = std of calib residuals, per day/night group |
| split_conformal | baseline (c) | point +/- conformal quantile of \|residual\| on calib, per day/night group |
| cqr_pooled | variant | CQR (Romano et al. 2019), one pooled calibration group |
| **cqr_mondrian** | **proposed** | CQR calibrated separately for day and night target slots (Mondrian conformal) |

CQR score on calib: s = max(lo - y, y - hi); the finite-sample conformal quantile q = the ceil((n+1)*level)-th
smallest score; interval [lo - q, hi + q] (q may be negative, which narrows an over-wide QR interval).

Why day/night groups: night targets are almost all exactly 0, so their scores are near 0. Pooling them with
day rows lowers the calibration quantile, which makes daylight intervals too narrow while the average
coverage still looks fine. Groups use the A2 `target_daytime` flag (prior-days irradiation envelope > 0.05),
which is known at the forecast origin. Gaussian and split conformal also get per-group calibration so that
they are fair baselines; `cqr_pooled` isolates the effect of grouping.

Applied identically to every method: bounds clipped to [0, 33,000 kW], widened if needed so that
lower <= point <= upper (the API requires this), and the night rule (below) sets the interval to [0, 0].

### Metrics
Per nominal level (80/90/95%), on scored test rows, for **all rows** and **daylight rows only**: empirical
coverage, mean width (kW), Winkler (interval) score = width + (2/alpha) * distance outside the interval (lower is
better), and pinball loss of the bounds read as the alpha/2 and 1-alpha/2 quantiles. Coverage is also broken
down by time of day of the target (dawn 05:00-08:59, midday 09:00-15:59, dusk 16:00-19:59, night) and per
test day (daylight rows).

### Exchangeability and a 4-day calibration set: what the guarantee does and does not say
- Split conformal methods guarantee marginal coverage >= the nominal level **only if** calibration and test
  scores are exchangeable (their joint distribution does not change when they are reordered). Time series
  break this: errors are autocorrelated within a day, weather regimes persist for days, and the season moves
  (mid-May to mid-June). Calibration days 06-09 to 06-12 and test days 06-13 to 06-17 are adjacent, but if the
  test days are cloudier or clearer than the calibration days, coverage will be off in a direction that has
  nothing to do with the method. So in this project the conformal guarantee is a design motivation, not a
  proof; the measured test coverage is what counts.
- Coverage is marginal: over all rows of a group, not per time of day, per day, or per forecast. Dawn and dusk
  can be under-covered while midday is over-covered and the average still hits the target. That is why
  coverage is reported by time of day and by day.
- Calibration size: about 188 daylight scored rows per plant (4 days x ~47 daylight slots). Even with i.i.d.
  data, split-conformal coverage for n calibration points varies around the nominal level with standard
  deviation of roughly sqrt(level*(1-level)/(n+2)), about 0.022 at 90% for n = 188. Because the rows are
  autocorrelated, the effective sample size is much smaller (closer to the number of days and weather
  situations, i.e. a handful), so the real variability is larger. The test set has 5 days, so the measured
  coverage is itself uncertain; per-day coverage is shown to make this visible. None of these results should
  be read as precise to better than several percentage points.

### Night-zeroing rule: decision (validation data only)
Candidates and criterion were fixed before the run: refit XGBoost and Random Forest (seeds 0-2, both plants)
under each rule; choose the lowest mean val MAE. The LSTM/TCN were not refit (CPU cost); this is a limitation.

| rule | mean val MAE (kW) | Plant 1 | Plant 2 |
|---|---|---|---|
| envelope <= 0.05 (A3 default) | 1395.3 | 1663.2 | 1127.3 |
| **envelope <= 0 (strict)** | **1387.4** | **1650.8** | **1123.9** |
| no night rule | 1396.3 | 1663.9 | 1128.8 |

**Decision: keep a night rule, but the strict one**: set the forecast (and interval) to 0 only when no
previous day ever had irradiation at T's time-of-day slot. The 0.05 threshold also zeroed dawn/dusk slots
with real output; dropping the rule entirely lets models predict small non-zero values on truly dark slots.
The gain is small (about 8 kW of val MAE, under 1%). The A3 table was produced with the 0.05 rule, so the
A5 comparison will be re-run with the strict rule for all models.

What the results show:
- **All-rows coverage overstates daylight coverage** by 3.5-6 points on Plant 1 at 90% for every method: night rows are
  almost always covered. Daylight numbers are the ones that matter.
- **Plant 1**: every method under-covers in daylight. The proposed `cqr_mondrian` gets closest to nominal at
  all three levels (daylight 0.789 / 0.887 / 0.939 at 80 / 90 / 95%) and has the best (lowest) Winkler score and
  pinball loss at every level, with intervals about 6% wider than `qr_raw`.
- **Plant 2**: the result is different. `cqr_mondrian` over-covers (daylight 0.872 / 0.957 / 0.979) with wider
  intervals, and **`qr_raw` has the best Winkler score and pinball loss at every level**. The proposed method
  is not better on Plant 2 (at 80% `qr_raw` ties with `cqr_pooled`); the calibration days required a larger
  correction than the test days needed.
- **Pooled calibration collapses**: on Plant 1 the pooled CQR correction was exactly 0 at all levels (seed 0),
  so `cqr_pooled` equals `qr_raw`. Cause: at night the quantile model predicts a lower bound of exactly 0 and
  the target is 0, so 86% of night calibration scores are exactly 0 and the pooled conformal rank falls inside
  that block. Calibrated on daylight rows only, the correction is +300 to +448 kW. This is the dilution effect
  that motivated the day/night grouping.
- The Gaussian and constant-width conformal baselines have much worse Winkler scores (about 18,200-18,300 vs
  about 14,800-15,000 on Plant 1 daylight): a constant width cannot shrink in the morning and evening, and it
  under-covers midday (Plant 1 midday coverage 0.78-0.79).
- **Where intervals fail** (90%, Plant 1): dusk is under-covered by every method except gaussian (0.82-0.84),
  midday by the constant-width methods (0.78-0.79). Per test day, `cqr_mondrian` daylight coverage ranges from
  0.848 (06-17) to 0.929 (06-16). The day-to-day spread (about 8 points) is larger than most differences
  between methods, which is consistent with the exchangeability and calibration-size caveats above.

Decision for the API (A6): the proposed `cqr_mondrian` at nominal 0.90 is the default interval, because it
had the best interval score on Plant 1 (the primary plant). Its over-coverage on Plant 2 is documented here.

## A5 Evaluation (`src/backend/forecasting/evaluation.py`)

Run: `python -m experiments.rolling_origin` (resumable; per-fold CSVs in `results/forecasting/a5_folds/`, about
5-8 min per fold on CPU), then `python -m experiments.evaluate_forecasting` -> `results/forecasting/a5_summary.md`
(all tables), `a5_*.csv`, figures `a5_rolling_mae.png`, `a5_rolling_coverage.png`, `a5_bootstrap_interval.png`,
`a5_error_by_hour.png`, `a5_error_vs_clearness.png`.

**One night rule everywhere**: the strict rule chosen in A4 (zero only where the prior-days envelope is 0) is
the code default. A3 and A4 were re-run with it; the old A3/A4 files (0.05 rule) are in
`results/forecasting/archive_night_rule_0.05/`. The A3 results table earlier in this document is the old-rule
version; the tables below replace it. Persistence got worse under the strict rule (Plant 1 test MAE 2369.2 ->
2458.0) because dawn slots are no longer forced to 0; the learned models moved by less than 20 kW.

### Protocol
- **Fixed split** (A2): test 06-13 .. 06-17, as in A3/A4.
- **Rolling origin (expanding window)**: 12 folds per plant, test days 06-06 .. 06-17. For test day d:
  train = all days up to d-9, val = d-8 .. d-5, calib = d-4 .. d-1, test = d. Minimum training window 14 days.
  Every model (point models and interval methods) is refit in every fold with seeds 0-2.
- **Paired day-level bootstrap**: per-day loss per model (seed-averaged), difference on the same days, days
  resampled with replacement (10,000 resamples, seed 0), 95% percentile CI. Point models: per-day MAE, all
  pairs. Interval methods: per-day daylight Winkler score, `cqr_mondrian` vs each other method.
  Coverage CIs: pooled daylight coverage with days resampled.
- MAPE is reported only on rows with y >= 1650 kW (5% of capacity); it is undefined near zero.
- No correction for multiple comparisons (about 15 point-model pairs and 12 interval comparisons per plant); a
  single CI that only just excludes 0 should be read with that in mind.

59.0% / 0.753. Plant 2: LSTM 1216.7 / 32.5% / 0.832, TCN 1227.7 / 32.3% / 0.832, RF 1230.2 / 35.4% / 0.821,
XGBoost 1241.7 / 35.5% / 0.819, persistence 1964.5 / 57.2% / 0.667. A MAPE of 32-35% on producing rows is high:
1-hour-ahead solar forecasting without weather forecasts misses cloud changes (the oracle-weather row reaches
5.5% on Plant 1).

### Intervals
**Plant 1 daylight coverage at nominal 90% (proposed `cqr_mondrian`)**:
- Fixed split (06-13 .. 06-17): **0.887, short of the 90% target by 1.3 percentage points.**
- Rolling origin (12 days, 06-06 .. 06-17): **0.893, short by 0.7 points; 95% day-bootstrap CI [0.853, 0.927]**.
  The CI includes 0.90, so with 12 days the shortfall cannot be distinguished from zero. Per day it ranges from
  0.73 (06-06) to 1.00 (06-09).
- For comparison, uncalibrated `qr_raw` on Plant 1: 0.846, CI [0.797, 0.879], short by 5.4 points; this CI
  excludes 0.90, so `qr_raw` under-covers.

Rolling origin, daylight, nominal 90% (coverage / mean Winkler, kW):

| method | Plant 1 | Plant 2 |
|---|---|---|
| qr_raw | 0.846 / 15324 | 0.889 / 13653 |
| gaussian | 0.882 / 17490 | 0.891 / 16619 |
| split_conformal | 0.905 / 17248 | 0.899 / 16830 |
| cqr_pooled | 0.854 / 15273 | 0.889 / 13666 |
| **cqr_mondrian** | **0.893 / 15135** | 0.906 / 13881 |

**Is the A4 split (cqr_mondrian wins on Plant 1, loses on Plant 2) real?** It is not established:
- Winkler, `cqr_mondrian` - `qr_raw` at 90%: Plant 1 -189 kW, CI [-1127, 548] (better on 5 of 12 days);
  Plant 2 +228 kW, CI [-47, 527] (better on 5 of 12 days). **Neither CI excludes 0.** The direction matches A4
  (slightly better on Plant 1, slightly worse on Plant 2), but over 12 days neither difference is resolved. The
  same holds at 80% and 95%.
- What is established is **calibration**: over the 12 days `cqr_mondrian` is within 1 point of nominal on both
  plants at all three levels (Plant 1: 0.807 / 0.893 / 0.951; Plant 2: 0.804 / 0.906 / 0.950), while `qr_raw`
  under-covers on Plant 1 by 5.2-5.7 points at every level, with CIs that exclude the nominal level. On Plant 2
  `qr_raw` is closer (0.761 / 0.889 / 0.948). The price is width: `cqr_mondrian` intervals are about 15% wider
  than `qr_raw` on Plant 1 and about 6% wider on Plant 2 at 90%.
- `cqr_mondrian` has a clearly better Winkler score than the Gaussian and constant-width conformal baselines on
  both plants at 80% and 90% (all CIs exclude 0; e.g. Plant 2 90%: -2737 kW vs gaussian, CI [-4171, -1387]).
  At 95% on Plant 1 the CI vs gaussian includes 0 ([-5917, 440]).
- `split_conformal` also reaches nominal coverage (Plant 1 0.905), but with a much worse Winkler score: a
  constant width is too wide at dawn/dusk and too narrow at midday.

Summary for the proposed method: over 12 rolling days `cqr_mondrian` delivers approximately nominal daylight
coverage on both plants, which `qr_raw` does not on Plant 1; its interval score is statistically
indistinguishable from `qr_raw` and clearly better than Gaussian or constant-width intervals.

### Error analysis
- **The dataset is only 34 days.** Every result rests on 12 rolling test days (5 for the fixed split) in one
  season (mid May to mid June). Nothing can be said about other seasons, the monsoon, or long-term degradation.
  Per-day MAE varies by a factor of about 2 across days (RF Plant 1: 1011 to 2137 kW), much more than the
  differences between learned models.
- **Errors by hour**: near zero before 06:00 and after 19:00; they rise through the morning and peak around
  midday to early afternoon (Plant 1 RF: 4294 kW at 12:00, 4415 kW at 14:00), when cloud-driven ramps are
  largest in absolute terms. Persistence is worst on the morning and late-afternoon ramps (5208 kW at 08:00 on
  Plant 1), where "same as an hour ago" is systematically wrong; learned models cut this by more than half.
- **Night-time residue**: under the strict rule, XGBoost leaves small non-zero predictions at night on Plant 2
  (3-55 kW per night hour), because the envelope there is slightly above 0 (small non-zero night irradiation
  readings). RF and the neural nets stay much closer to 0. The effect on MAE is small but visible hourly.
- **Weather dependence**: on Plant 2 the learned models do worse on cloudier days (Spearman rho between daily
  clearness and daylight MAE -0.43 to -0.71; the cloudiest day 06-11 had about double the daylight MAE of the
  clearest day 06-08). On Plant 1 there is no clear relation for the learned models (rho -0.13 to 0.22). With
  12 days these correlations are indicative only.
- The oracle-weather row (measured irradiation at T, not deployable) remains far better (Plant 1 fixed split
  293.7 kW), so the main limitation is the absence of weather forecasts, not the choice of model.
- The dawn/dusk issue noted in A3 is resolved by the strict rule, which no longer forces 0 where there is output.

## A6 Forecast API (`POST /forecast`)

Code: `src/backend/forecasting/service.py` (model build + serving), `schemas.py` (request/response),
endpoint in `src/backend/main.py`. Build the deployed models once:
`python -m experiments.build_forecast_model` -> `models/forecasting/solar_plant{1,2}.joblib` (gitignored, about
2-4 MB each) and `results/forecasting/a6_model_card.json`. The API loads a plant's artifact on first use; if it is
missing the endpoint returns **503** with the build command. The model directory can be changed with
`GREENRAG_FORECAST_MODEL_DIR`. Artifacts are joblib pickles and must only be loaded from this local folder.

Request:
```json
{"plant": 1, "origin": "2020-06-16T11:00", "confidence": 0.9}
```
- `plant`: 1 or 2. `origin`: the last observed 15-min slot, naive local plant time, on the 15-min grid, inside
  the record (2020-05-15 00:00 .. 2020-06-17 23:45). Off-grid, time-zone-aware or out-of-range origins -> 422.
- `confidence`: 0.80, 0.90 (default) or 0.95, the levels the intervals are calibrated for; anything else -> 422.
- There is no live telemetry feed, so the service forecasts from the stored plant data, using only data at or
  before `origin` (tested by corrupting everything after the origin, with a positive control).

Response (the four plan fields plus context):
```json
{"prediction": 20849.3, "lower_bound": 10590.4, "upper_bound": 26894.1, "confidence": 0.9,
 "plant": 1, "origin": "2020-06-16T11:00:00", "target_time": "2020-06-16T12:00:00", "horizon_minutes": 60,
 "observed_kw": 7269.3, "in_sample": true, "daylight_group": true, "method": "cqr_mondrian", "unit": "kW",
 "model_version": "plant1 <trained_at> (fit on 2020-05-15..2020-06-17)"}
```
(Real output from the built model; this particular interval misses the observed value, which a 90% interval
is expected to do about one time in ten.)

- **confidence = the nominal coverage level of the interval** (definition in A4; also in the OpenAPI schema).
- `in_sample` is true when `target_time` falls on a day the model was trained, tuned or calibrated on. With the
  deployment split below this is every target inside the record; only origins in the last hour of 2020-06-17
  (targets on 06-18) are true out-of-sample forecasts. Measured performance is in A4/A5, not in these calls.
- `observed_kw` is the measured value at `target_time` when it exists in the dataset.

Deployed model (per plant): XGBoost point forecast + multi-quantile XGBoost + `cqr_mondrian` intervals, strict
night rule, horizon 1 h. Split follows the rolling-origin protocol aimed at the day after the record: train
2020-05-15 .. 06-09, val 06-10 .. 06-13 (hyperparameters, early stopping), calib 06-14 .. 06-17 (conformal
offsets). CQR offsets at 90%: Plant 1 daylight +185.8 kW, Plant 2 daylight +82.8 kW, night 0 for both
(`a6_model_card.json`). XGBoost rather than RF/LSTM is the point model because the A4/A5 interval methods were
built and evaluated on it; A5 found no resolved difference between XGBoost and LSTM/TCN, and RF was better than
XGBoost on Plant 1 by 63.5 kW (about 4%).

Known limitation: Plant 2 night irradiation readings are slightly above 0, so the strict night rule does not zero
some Plant 2 night slots, and the API can return small non-zero night forecasts there (e.g. origin 2020-06-17
23:45, target 00:45: prediction 98 kW, interval [0, 592]). This is the night residue noted in A5; any change to
the rule must again be chosen on validation data.

Tests: `tests/test_forecast_api.py` (TestClient): request/response validation, OpenAPI description of
`confidence`, day/night/out-of-sample responses, wider level -> wider interval, 422/503 errors, existing endpoints
still working, API interval identical to the offline A4 `cqr_mondrian` computation, and no use of data after the
origin (with positive control).

## Wind T1 replication of Track A (`src/backend/forecasting/wind.py`)

Run: `python -m experiments.wind_rolling` (resumable, per fold/model/seed CSVs in
`results/forecasting/wind/folds/`, about 1.5 h on CPU), then `python -m experiments.wind_evaluate`
(`results/forecasting/wind/wind_summary.md`, CSVs, figures `wind_monthly_mae.png`, `wind_coverage_regime.png`,
`wind_error_by_speed.png`) and `python -m experiments.wind_diagnose` (`wind_diagnosis.md`).

### Decisions
- **Resolution and horizon**: native 10-min grid, **1 hour ahead (6 steps)**. With a full year (52,560 slots)
  hourly resampling would still leave enough data, but it would average away ramps and require a different
  horizon definition; 1 hour keeps the solar and wind tracks comparable and is an intraday balancing horizon.
  The data has no weather forecasts. Lags 1/3/6/24 steps = 10 min, 30 min, 1 h, 4 h. Power autocorrelation is
  0.92 at 1 h and only 0.34 at 24 h, so unlike solar there is no dominant daily cycle.
- **Preprocessing** (same steps as A1, adapted): one turbine, no plant aggregation; 3.9% of slots missing (longest
  gap 4.3 days); 57 slightly negative power values (>= -10 kW, auxiliary consumption) clipped to 0 and flagged;
  1,343 downtime slots (power <= 10 kW while the power curve says >= 500 kW) flagged and kept; weather inputs
  forward-filled for at most 20 min; target never imputed. The trailing robust-z outlier flag on
  (power - power curve) marks 9.4% of slots: at low wind both are about 0, the MAD is tiny and z inflates. The flag
  is loose and is not used for any decision.
- **Features**: power lags/rolling stats as for solar; wind speed, direction (sin/cos), power-curve value and
  wind-speed ramp/volatility at or before the origin; calendar of T including day-of-year. Oracle row: measured
  wind speed and power-curve value at T (upper bound only). Causality tested as for solar (future corruption with
  a positive control; preprocessing prefix invariance).
- **Models**: unchanged code. Scaled settings for ~15x more data on CPU: RF 200 trees, grid max_depth {12, 20} x
  min_samples_leaf {1, 5}; LSTM/TCN batch 256, at most 60 epochs, patience 8. The day/month ablation was dropped.
- **No night rule** for wind (`night_threshold=None`); predictions clipped to [0, 3,780 kW] (rated 3,600 x 1.05).
- **Intervals**: unchanged methods. Mondrian groups = power regime of the point forecast (known at the origin):
  low < 10%, mid, high >= 90% of rated, fixed in advance. This is the analogue of solar day/night: near-constant
  low-output periods would otherwise dilute the calibration.
- **Evaluation**: rolling origin by month. Test months Sep-Dec 2018; for test month m: train = all months before
  m-2, val = m-2, calib = m-1. 16,330 scored rows over 116 days; seeds 0-2; paired day-level bootstrap.

### Results (rolling origin, pooled over Sep-Dec 2018)

| model | MAE (kW) | nMAE | RMSE (kW) | R2 |
|---|---|---|---|---|
| **persistence** | **298.1** | **8.28%** | 490.9 | 0.8619 |
| daily_persistence | 1157.1 | 32.14% | 1573.1 | -0.4184 |
| random_forest | 343.2 +/- 1.1 | 9.53% | 486.4 +/- 0.8 | 0.8644 |
| xgboost | 329.6 +/- 1.7 | 9.16% | **480.3 +/- 1.6** | **0.8678** |
| lstm | 365.1 +/- 6.0 | 10.14% | 523.8 +/- 14.5 | 0.8427 |
| tcn | 339.8 +/- 8.2 | 9.44% | 498.5 +/- 5.6 | 0.8576 |
| xgboost + oracle wind (upper bound) | 114.8 | 3.19% | 216.9 | 0.9730 |

- **Persistence has the lowest MAE; no learned model beats it on MAE.** Day-level bootstrap: persistence minus
  XGBoost = -33.6 kW, CI [-43.7, -24.4], persistence better on 87 of 116 days; likewise vs RF, LSTM, TCN (all CIs
  exclude 0).
- On **RMSE** and R2, XGBoost and RF are slightly better than persistence (480.3 and 486.4 vs 490.9).
- **Why** (`wind_diagnosis.md`): the models are trained on squared error and predict conditional means. On flat
  hours (power changed < 1% of rated; 30.6% of rows) persistence errs by 5.5 kW and the learned models by
  122-160 kW; at ~0 power and at rated power likewise. On ramps (> 10% change; 29.8% of rows) the learned
  models are better (686-699 vs 765.5 kW), and in the mid-power band too (403-429 vs 444.9 kW). So the learned
  models capture ramps but pay on the many flat stretches, which MAE weights heavily.
  Not changed here: an MAE/quantile objective or a persistence blend would have to be chosen on validation data.
- Among learned models: XGBoost is best (better than RF by 13.0 kW, CI [7.1, 19.2]; than LSTM by 30.8 kW);
  XGBoost vs TCN is not resolved (-6.8, CI [-14.7, 2.2]).
- The oracle row shows again that future weather is the missing information.

Intervals (90% nominal, point model XGBoost): `cqr_mondrian` coverage **0.890, CI [0.869, 0.909], short by 1.0
point** (the CI includes 0.90); `cqr_pooled` 0.893; `qr_raw` 0.866 (short 3.4, CI excludes 0.90);
`split_conformal` 0.904; `gaussian` 0.927 (over-covers). Winkler: `cqr_mondrian` 1846 vs `qr_raw` 1847 (difference
-3 kW, CI [-11, 3], not resolved); vs gaussian and split conformal -53 kW (CIs include 0 at 90%, exclude 0 at 80%).
**By regime, all quantile-based methods under-cover when the forecast is high** (predicted >= 90% of rated,
10% of rows): `cqr_mondrian` 0.698, `qr_raw` 0.559, whereas split conformal (0.890) and gaussian (0.934) cover
there. The regime grouping helped only a little (0.698 vs pooled 0.662); a sudden drop from rated power
(cut-out, curtailment, downtime) is what the high-regime intervals miss.

### What carried over unchanged, and what did not
- Unchanged: the model classes, the interval methods, the bootstrap/coverage code, the API service.
- Generalised with solar defaults preserved (all 190 tests pass; solar /forecast output identical): capacity and
  night rule are parameters; the sequence encoder takes its input and context columns; interval groups can be
  any labels; `cqr_offsets` takes a group list.
- Wind-specific: preprocessing, features, month folds, regime groups (`wind.py`).

### API
`POST /forecast` now accepts `asset` (`solar_plant1`, `solar_plant2`, `wind_t1`) or the legacy `plant` (1, 2);
exactly one must be given. The origin grid is per asset (15 min solar, 10 min wind). New response fields:
`asset`, `calibration_group` ("daylight"/"night" or "power regime low/mid/high"); `plant` and `daylight_group` are
null for wind. The deployed wind model follows the same protocol aimed at the period after the record: train
Jan-Oct, val Nov, calib Dec 2018 (`python -m experiments.build_forecast_model`). Given the results above, the
deployed wind point forecast (XGBoost) has a higher MAE than persistence; this is documented, not hidden.
